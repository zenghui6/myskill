# 设计文档工作流

## 查找顺序

1. 项目 `docs/design/`。
2. `{USER_DOCUMENTS}/ai-docs/{project}/design/`。
3. 优先读取 `{需求名}-current.md`；完整档同时读取 `{需求名}-coding.md`。
4. 稳定文档不存在时，快照只作为参考，不替代新的稳定文档。

## 目录与命名

独立需求放在 `design/{需求名}/`；属于已有架构的子模块放在 `design/{父需求}/{子模块}/`，最多嵌套两层。稳定文件使用 `-current.md`，完整档编码摘要使用 `-coding.md`，接口文档使用 `-api-current.md`。

## 新建流程

1. 读取 design 索引，判断已有主题、内容重叠和父级归属。
2. 回显目标路径和档位。
3. 使用对应模板创建或更新稳定文档。
4. 更新 design 索引。
5. 完整档生成编码摘要；涉及接口时补接口文档。
6. 等待用户确认后进入实施。

## 变更流程

需求变化时直接更新稳定文档，并同步 coding 摘要和接口契约。只有重大架构基线、发布基线、用户明确要求或非 Git 管理场景才创建 `snapshots/`。

## 实现完成后的闭环

实现完成后（用户确认验收或代码合入）：

1. 对照设计文档的状态机、表设计、接口契约章节与实际代码，识别「新增/变更的结构事实」。
2. 写入 `backend-knowledge-graph-required` 候选池（`_candidates.md` / `_sql_candidates.md`），带证据位置；实现与设计有偏差时以代码为准并回填设计文档差异。
3. 分期实现的需求每期只沉淀本期增量；同主题候选合并更新，冲突记录不覆盖。
4. 极简档不产生结构事实，跳过。
